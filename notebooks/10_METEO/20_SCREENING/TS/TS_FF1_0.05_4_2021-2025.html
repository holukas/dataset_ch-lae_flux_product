MeteoScreening TS_FF1_0.05_4 (2021-2025) from database (influxdb)

Modified

4 September 2026

Site: CH-LAE   |   Variable: TS_FF1_0.05_4   |   Sensor: Campbell 109 thermistor, analogue, added at the March 2021 logger rebuild   |   Period: 2021-2025 Derived from: diive notebook template DatabaseInfluxStepwiseMeteoScreening.ipynb (version 9, 15 Jul 2026), via TS_FF1_0.05_1_2020-2025.ipynb Author: Lukas Hörtnagl (holukas@ethz.ch)

ℹ️ About this notebook

Download raw soil temperature from the InfluxDB database, remove the worst outliers on the high-resolution data, resample to 30MIN, and upload the result back to the database. Screening uses StepwiseMeteoScreeningDb from diive (diive/preprocessing/qaqc/meteoscreening.py); download and upload use diive’s in-house InfluxDB engine (InfluxIO, in diive/core/io/db/influx).

Flow: download (InfluxIO) → screen on high-res data (diive) → resample to 30MIN → upload.

Scope is deliberately narrow. The raw record is millions of rows, so anything done here is expensive. This notebook only takes out what is unambiguously wrong at high resolution — the 2022 fault window (manual removal) — and hands over a clean 30MIN series. Everything else (sensor comparisons, level/offset questions, gap handling, homogenisation across sensor generations) is settled later in 30_PRODUCTS/, on the half-hourly data, where it costs a fraction as much.

Outlier detection is stepwise: run a test, inspect its preview plot, then commit it with mscr.addflag(). Re-run with different parameters as often as you like before committing. Run only the tests a variable actually needs. At the end all committed flags are aggregated into one overall quality flag QCF.

Which sensor this is. In this profile the replicate suffix names the sensor family, not the depth: _1 = the water-potential sensors of the 19 Mar 2020 install (MPS-2 at 0.05/0.1/0.6 m, TEROS 21 at 0.2/0.3/0.5 m), _2 = the TEROS 12 probes that also report SWC_FF1_<depth>_1, _3/_4 = Campbell 109 thermistors added at the March 2021 logger rebuild. This one is a Campbell 109 thermistor (analogue, not on the SDI-12 bus). Being analogue rather than SDI-12 is what makes this notebook differ from its _1/_2 siblings, in three places marked below.

Database access needs the influxdb-client package, which this project pulls in via the diive[db] extra (declared in pyproject.toml). diive also ships a db dependency group, but dependency groups are local to the project that declares them — uv sync --group db only works inside the diive repo, not from here.

⏱️ Timestamp convention (important)

The database stores every timestamp in UTC and as TIMESTAMP_END (the stamp marks the end of the averaging interval). Getting this right is the one thing that must not go wrong: the value written back to the database depends on it, and so does every window in REMOVE_DATES.

The single knob is TIMEZONE_OFFSET_TO_UTC_HOURS (set in User settings). It is applied identically on download and on upload:

Stage Timezone Convention Done by
Database UTC TIMESTAMP_END InfluxDB
After dbc.download(..., timezone_offset_to_utc_hours=N) local (UTC+N) TIMESTAMP_END InfluxIO
During screening local TIMESTAMP_MIDDLE (converted internally) StepwiseMeteoScreeningDb
After mscr.resample() local back to TIMESTAMP_END diive
After dbc.upload_singlevar(..., timezone_offset_to_utc_hours=N) UTC TIMESTAMP_END InfluxIO

One place where this bites. REMOVE_DATES is matched against TIMESTAMP_MID, not TIMESTAMP_END: StepwiseMeteoScreeningDb hands the series to ManualRemoval after the internal conversion, so the record whose TIMESTAMP_END is 10:39:00 carries the label 10:38:30 inside the test. A bare '2025-12-19 10:39:00' would therefore match nothing and the removal would silently do nothing. It only matters when removing individual records: a window spanning days has edges far larger than the half-record offset.

✏️ User settings (please adjust)

Adjust these before running. What each setting means:

Site - SITE, SITE_LAT, SITE_LON: site ID and coordinates. The coordinates set the day/night split used during screening — not used here, see Outlier detection.

Variable to screen - PROFILE, DEPTH, REPL: the sensor’s position tags. FIELD is assembled from them and is the InfluxDB _field. REPL changes the sensor family, not just the probe. - MEASUREMENT: exactly one measurement grouping the variables — TS for soil temperature.

Time range to screen - START: first timestamp to screen — is included. - STOP: upper bound — is not included.

Data settings - TIMEZONE_OFFSET_TO_UTC_HOURS: the critical timestamp knob — see Timestamp convention. Must match how the raw data was logged (1 for CET winter time) and must be the same value everywhere. - DATA_VERSION: the source data version in the database (raw). - DIRCONF: local folder holding the database connection config.

Resampling - RESAMPLING_FREQ / RESAMPLING_AGG: soil temperature is a state, so 'mean' — never 'sum'.

Physical range - TS_MIN, TS_MAX: the absolute-limits test, justified from this sensor’s own measured extremes.

Parameter help - SHOW_PARAM_HELP: True prints the full docstring of each screening method right before it runs.

# --- Time range to screen ---
# This channel was added at the March 2021 logger rebuild and first logged on
# 2021-03-26 15:22, so it has a SINGLE resolution era: 1MIN throughout. Asking for
# 2021-01-01 simply starts at the first record. Nothing before 2021-03-26 belongs to
# this series - the Campbell 107 thermistors it replaced live under different names.
START = '2021-01-01 00:00:01'  # included
STOP = '2026-01-01 00:00:01'  # not included

# --- Data settings ---
DATA_VERSION = 'raw'
TIMEZONE_OFFSET_TO_UTC_HOURS = 1  # UTC+01:00 (CET, winter time). Must match how the raw data was logged.
DIRCONF = r'F:\dev\poet\configs'
# DIRCONF = r'P:\Flux\RDS_calculations\_scripts\_configs\configs'

# --- Resampling ---
RESAMPLING_FREQ = '30min'  # screened high-res data is resampled to this frequency
RESAMPLING_AGG = 'mean'  # (!) soil temperature is a state variable, never summed

# --- Physical range of soil temperature at this site, in degC ---
# (!) DELIBERATELY WIDER THAN ITS SIBLINGS, and that is not an oversight.
# This channel's measured range over 2021-2025 is -5.49 to +31.53 degC - but those extremes are
# the 2022 fault window, which the manual removal above takes out by name. Keeping the limits at
# [-5, 30] would mean the absolute-limits test silently ate the edges of that fault as well,
# so that narrowing the window later would quietly leave part of it removed by a test that was
# never meant to police it. Each test does one job: the window removes the fault, and these
# limits are a backstop against an open-circuit thermistor railing. Outside the fault window
# this channel behaves like its twin, 1-20 degC.
TS_MIN, TS_MAX = -15, 45

# --- Parameter help ---
SHOW_PARAM_HELP = False

🔍 Outlier detection

Run a test → inspect its preview → commit with mscr.addflag(). Only the committed flag of the most recent test is added. Skip any test a variable does not need.

What is committed here: the 2022 fault window (manual removal), a physical-range backstop (absolute limits), and the missing-values flag. Why the rest are off:

  • Never split day and night. Soil temperature does have a diurnal cycle, but at this depth it is damped and lagged relative to the surface, so a solar-geometry split does not line up with it — it would only halve the sample behind every threshold. Every test below runs with separate_daytime_nighttime=False.
  • Distribution-wide tests measure the season, not a fault. A z-score over the whole record asks how far a value sits from the multi-year mean; January at 2 °C and July at 19 °C are both correct.
  • Differencing-based tests would actually work here — and are still not committed. This is the one place where this notebook differs from its _1/_2 siblings on a point of arithmetic rather than taste. Those channels are SDI-12 and quantised to a 0.05 °C grid, which collapses the rolling MAD a Hampel filter scales its band by to exactly zero. This one is an analogue thermistor: its values are continuous (only 0.007 % land on that grid, i.e. at chance) and it has a single 1MIN resolution era with no back-filling. So a spike test has a real scale to work with. It is left off because there is nothing for it to find, not because it would misbehave — see Other tests below. If any channel in this family ever justifies one, it is this one.

Manual removal

Flag specific timestamps or time ranges for removal - known sensor failures, maintenance windows, logger artefacts. Give [start, stop] pairs and/or single timestamps.

This is the one channel at 0.05 m that needs a substantial window, and it is also the only thing in this notebook that deletes data on a person’s say-so — so the cell below re-derives its own justification from the downloaded record on every run and refuses to proceed if the evidence has changed.

Between 2022-02-24 and 2022-05-12 this thermistor swings ±25 K a day. Soil at 0.05 m under a mixed forest cannot do that; the litter layer alone damps the surface signal far below it, and this channel’s own twin TS_FF1_0.05_3 — the same make of sensor, the same nominal depth, a few metres away — sits at 1.8-9 °C with a 0.5-1.3 K amplitude through exactly the same weeks. The reading is not soil temperature. The most likely explanation is that the probe was out of the ground, but the fieldbook records nothing for the period, so the removal rests on physical evidence alone.

⚠️ A second, quieter episode is not removed here. After the 23 Oct 2025 windstorm this channel shows a median daily amplitude of 3.38 K in Nov 2025 and 1.86 K in Dec 2025, against 0.37-0.71 K in every earlier Nov/Dec. That is elevated but an order of magnitude below the 2022 fault, and the storm is documented as damaging above-ground sensors. It is left in the record and flagged for 30_PRODUCTS/ to settle on the 30MIN data, where the comparison against 0.05_3 is cheap. Removing it here on a hunch would be exactly the hand-removal-in-disguise this folder warns about.

On the open fieldbook question. A 2026-07-17 CHECK entry asks whether this sensor is “too close to the surface? Very strong daily cycle”. Outside the two episodes above the record does not support that: this channel runs at 1.0-1.7 K summer amplitude against 0.9-1.2 K for 0.05_3. The strong cycle is episodic, not permanent.

Absolute limits

Flags values outside a fixed physical range [minval, maxval]. On this channel it is a backstop, not a workhorse: being analogue, it never saw the SDI-12 decode garbage that this test exists to catch on the _1/_2 channels. What it guards against is an open-circuit or shorted thermistor, which rails rather than returning a plausible number. Expect it to flag nothing, and treat it flagging anything as news.

⚠️ Do not clip instead. correction_setto_max_threshold would turn a railed reading into a fabricated in-range value that nothing downstream could identify as fake. A removed value is honest; a clipped one is not.

Other tests (all off)

Left switched off — but for a different reason than in the _1/_2 notebooks, and the difference matters if you ever reach for one.

There, differencing-based tests are broken: quantisation collapses their scale estimate to zero. Here they are merely unnecessary. This channel is analogue and continuous, on a single 1MIN grid, so a Hampel filter has a real MAD to work with and would behave sensibly. The reason not to commit one is that there is nothing left for it to find once the manual removal has run — and a spike test on a 1MIN soil record mostly rediscovers the fact that soil temperature is smooth.

If you do enable one: there is no per-era split to worry about on this channel (single resolution era), but differencing-based tests still compute their differences after dropping missing records, so the records flanking every gap are compared across the gap and look like spikes. Check what it flags against the gap list before believing it.

Applied to the high-res, QCF-filtered data. None of them apply to soil temperature, and every call below stays commented out. The corrections diive offers are offset removals for radiation and relative humidity, threshold clipping, and setting ranges to a constant - every one of them writes a value the sensor did not measure.

This is an analogue channel and has no such sentinel — but do not enable that call anyway, for the plainer reason that 0.00 °C is a perfectly possible soil temperature.

⬆️ Upload data to database

Re-uploading overwrites the same variant - safe to re-run. With delete_from_db_before_upload=True (below), the upload first deletes, then writes. The delete is scoped to the exact match _measurement + varname + data_version (meteoscreening_diive) over the uploaded time range, so re-screening a period replaces only its previous screened result. It never touches the raw data (different data_version, and a different _raw bucket), other variables, or other data versions. The delete-first step (rather than a plain overwrite) matters because InfluxDB keys a point by its full tag set: if a tag changed between runs (e.g. units, gain, offset), a plain write would leave the old point as a duplicate - the delete removes it regardless of tags.

📝 Notes for this variable

  • Mean, not sum. RESAMPLING_AGG = 'mean' - soil temperature is a state, not a flux.
  • Units are °C, filegroup 12_meteo_forestfloor.
  • Sensor identity. Campbell 109 thermistor, analogue, added at the March 2021 logger rebuild and first logged 2021-03-26 15:22. Nothing before that date belongs to this series.
  • Coverage 2 479 116 records, 98.02 % over 2021-2025. It logged straight through the April 2024 SDI-12 bus failure.
  • Measured range −5.49 … 31.53 °C — and both extremes are the 2022 fault window, not a colder or hotter spot. Outside it this channel behaves like its twin, 1-20 °C.
  • A single resolution era, 1MIN throughout. Values are continuous, not quantised — differencing-based tests are viable here, unlike on the SDI-12 channels.
  • Not on the SDI-12 bus, so neither the December 2025 artefact minutes nor the April 2024 decode garbage exist in this record.
  • The 2022 fault is removed; the post-storm episode is not. Median daily amplitude 22.36 K in March 2022 (against 1.30 K in March 2023) versus 3.38 K in Nov 2025 (against 0.37-0.71 K in earlier Nov/Dec). The first is not soil; the second is elevated but ambiguous, and is left for 30_PRODUCTS/ to settle against 0.05_3 on the 30MIN data.
  • The open fieldbook question is not supported by the normal record. The 2026-07-17 CHECK asks whether this sensor sits too close to the surface. Outside the two episodes it runs at 1.0-1.7 K summer amplitude against 0.9-1.2 K for 0.05_3 — a difference, but not the “very strong daily cycle” the entry describes. The strong cycle is episodic.
  • Deferred to 30_PRODUCTS/, on the 30MIN data: the comparison against the rest of the FF1 profile and against air temperature, the placement and offset questions, and any gap handling. This notebook exports gaps where the station was down and does not fill them.

♻️ Sibling notebooks

This is the only notebook at 0.05 m whose REMOVE_DATES deletes a substantial stretch, so it is the only one where the removal cell re-derives its own evidence from the data. If you narrow or widen the window, the assertion tells you whether the evidence still supports it — do not weaken the assertion to make a window fit.

The standing rule for all of them: REMOVE_DATES belongs to a sensor, not to a variable. These notebooks are copies of each other with a few settings changed, and carrying a window across a copy deletes good data under a justification written about a different probe.
